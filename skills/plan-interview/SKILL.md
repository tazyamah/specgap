# 初回の対話で plan を作る

人が最初に話した内容（アプリの望み）から、短い一問一答を繰り返して plan の仕様書（①）を作る。道具は台帳（JSON）で、`python -m specgap_lang interview` の `status`（次に聞くこと）と `render`（plan の Markdown）を使う。台帳は plan の元であり、コードから作らない。

## 約束

- **1回に聞くのは1問**。短く。長い一覧を見せて全部答えさせない。
- **AI が決めたことは書かない**。決まっていないことは問い（questions）にする。意図的に決めない場合は status を `unspec`（未規定）にする。「まだ聞いていない」と「決めない」を混ぜない。
- 曖昧な答えは具体例で確かめる（「たとえば〜の場合は？」）。番号だけの答えは、どれと受け取ったかを返す。
- 答えを受けるたびに台帳へ書き、judgments に「問い・答え・誰が・いつ」を1行足す。
- 作りこみの手順（この聞き方）と、アプリの動作を混ぜない。台帳のユースケースにはアプリの動作だけを書く。

## 進め方（Cockburn の外側から内側へ）

1. **範囲**：作るものの一言（summary）と範囲外（out_of_scope）。範囲外は PMBOK のスコープ記述書の考え方。
2. **アクターと目標の一覧**：「誰が、何をしたいか」を1行ずつ。「他に使う人は？ 他にやりたいことは？」で足りないものを聞く。目標の粒度（要約／利用者目標／下位機能）を付ける。利用者目標を基本にする。
3. **目標ごとの肉付け**（1目標ずつ、ここを繰り返す）：
   1. 主な流れ（成功の道）を3〜9手で。
   2. 失敗・例外・分岐（拡張）：「この手がうまくいかなかったら？」を手ごとに聞く。
   3. ルール（青）→ 具体例（緑）→ 未解決の問い（赤）に分けて聞く。具体例は前提・操作・期待で書く。
   4. 未解決の問いが0（または意図的に未規定）になったら、その目標は終わり。
4. **付加情報の仕分け**：人は1つのユースケースへの返答に、別のユースケース・動作要件・制約・品質（速さなど）を混ぜる。気づいたら extras に書き、`kind`（runtime／constraint／quality／other）で仕分け、元の目標には残さない。別の目標に当たるものは usecases に足す。
5. **動作要件**（コードを書き始める前）：ユースケースが固まったら `status` が R1〜R7 を示す。溜まった extras を先に見せ、足りないものを1問ずつ聞く。少なくとも **R1（動作プラットフォーム）は確定**させる。R8 以降（認証、量、止まってよい時間、性能、個人情報・法令、多言語、運用、移行）は、ユースケースから必要と分かったものだけ聞く。出典は notes/spec-runtime-requirements-checklist.md。
6. `status` が「コードを書き始めてよい: はい」になったら、`render` で plan を出して人に見せる。レビューを経てからコードに起こす。

## 台帳の書き方

`interview init 台帳.json --title 題名` で作る。形は specgap_lang/interview.py の冒頭を見る。JSON は Edit で直接直してよい。書いたら必ず `status` を実行し、次に聞くことを確かめる。
