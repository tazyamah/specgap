# specgap：仕様の漏れ検査器とレビュー画面（試作）

人がコードを読まずに仕様だけをレビューする前提で、次のことを行う試作です。

1. **仕様そのものの漏れ**を機械的に見つけ、人がそのまま答えられる問い（「経過日数=30、商品状態=開封済み のとき、どうしますか」）を返す（試作0）
2. 正本（YAML）から**人が判断するためのレビュー画面**を生成する。人は正本を読まず、ユースケース図・画面遷移図・決定表と具体例・状態の表・前の版との差分だけを見る（試作1）
3. **システム間の連携**を正本に書き、検査し、画面に出す。外部への作用は取り消しにくくデータも外に出るので、人の判断が一番集まる場所として扱う（試作2）
4. **実装が仕様に従っていること**を項目ごとに確かめ、保証の段階（証明済み・テスト済み・なし、監視の有無）を出す。正本に書いた方針に届かない実装は受け入れない（試作3）
5. **外部とのやりとりの実装**を模擬の外部の中で動かし、手順の順序・使ってよい外部作用とデータ・失敗の扱い・途中で止まったときの再開を確かめる。実装が使った外部作用は権限の一覧として画面に出す（試作4）
6. **問いに答えると正本が更新される**。答えが正本のどこにどう入るかは機械が決め、新しい版を書き出してもう一度検査する。人も AI も正本を手で直さない（試作5）
7. **判断を正本のオブジェクトにする**。答えるたびに判断（ADR に当たる）が残り、表の行やルールはどの判断から来たかを持つ。実装は表と状態機械を判断に任せ、結果に理由が付く（試作6）
8. **道具で受けられなかった答えを受ける**。確認の問いへの「このままでよい」を判断として残し、選択肢に収まらない答えは正本の変更案として機械が当てて検査し直す（試作7）
9. **画面の入口を複数書く**。通知メールのリンクのように、最初の画面を通らずに画面を開く入口を正本に書き、検査と図に入れる（試作8）
10. **失敗の扱いを手順で書き、実装が従っているかを確かめる**。人の言葉は残したまま、AI が手順に置き換え、模擬の外部で分かれ道ごとに実装を動かす（試作9）

11. **独自構文 → Rust 生成と plan の仕様書との突合**を最小で通す（`specgap_lang/`、お店の例の受注と決済要求）。詳細は `specgap_lang/README.md`

役割分担は「人の意思を AI が受け取り、会話で仕様が決まり、AI が実装し、抜け漏れは機械が保証する」です。
正本は AI が書き機械が検査するもので、人向けの表示は毎回そこから作り直すので、図と仕様がずれません。

設計の背景は Claude Doc「レビュー面と保証レベル 詳細設計」の「仕様の漏れ検査」節を参照してください。

## 使い方

```
pip install -r requirements.txt
python -m specgap check examples/refund_v1.yaml           # 漏れを検査（Markdown）
python -m specgap check examples/refund_v1.yaml --json    # JSON で出力
python -m specgap view examples/shop_v2.yaml --base examples/shop_v1.yaml -o views/shop_v2.html
                                                          # 前の版との差分付きレビュー画面
python -m specgap check examples/shop_v2.yaml --impl examples/impl/shop_impl_bug.py
                                                          # 実装を差し替えて確かめる（バグ入りの例）
python -m specgap questions examples/shop_v1.yaml         # 答えると正本を直せる問いの一覧
python -m specgap answer examples/shop_v1.yaml examples/answers/shop_v1.yaml -o examples/shop_v1_answered.yaml
                                                          # 答えを正本に書き込み、新しい版を検査
python -m specgap ask examples/shop_v1.yaml              # 次の1問（会話で1つずつ聞く）
python -m specgap reply examples/shop_v1.yaml <問い> <答え> --said "<人の言葉>"
                                                          # 答えを1つ反映して検査し直し、次の1問
python -m specgap change examples/shop_v1.yaml ops.yaml --title "<決めたこと>" --said "<人の言葉>"
                                                          # 選択肢に収まらない答えを、正本の変更として当てる
python -m specgap decisions examples/shop_v1_interviewed.yaml -o decisions/shop_v1_interviewed
                                                          # 判断を ADR 形式の Markdown に書き出す
python -m pytest -q                                       # テスト
```

`check` の終了コードは、受け入れ可なら 0、拒否する漏れがあれば 1、仕様ファイルが読めなければ 2 です。
`python -m specgap <仕様>` のようにサブコマンドを省くと `check` になります。

## レビュー画面に出るもの

上から「答えること → 変わったこと → 全体像 → 詳細」の順に並べています。

| 節 | 中身 | 正本のどこから作るか |
| --- | --- | --- |
| 答えてほしいこと | 検査器の問い（拒否・確認）と具体的な入力 | 検査結果 |
| 前の版からの変更 | 結果が変わる具体例（前の版と今の版で同じ入力を計算）、書き換わった箇所 | 2つの版の差分 |
| 誰が何をするか | ユースケース図と一覧 | actors / usecases |
| 画面の流れ | 画面遷移図（追加は緑、削除は赤の破線） | screens |
| 決まりごと | 決定表（穴は「どうしますか」の行として表示）、各行の具体例、いつでも成り立つこと | tables / ensures |
| 状態の移り変わり | 状態遷移図と「状態 × 出来事」の表（空欄が無いことが漏れが無いことを示す） | machines |
| システムのつながり | システム構成図、外に出ていくデータ（区分を超えたものは赤）、取り消せるかと二重実行を防ぐキー | systems / data / effects |
| 処理の流れ | 操作ごとのシーケンス図（問いが出ている手順は赤・黄）と、途中で止まったときの扱い | operations の steps |
| 実装が仕様どおりか | 項目ごとの事前の保証・実行時の監視・根拠（違反は具体例）・方針、前の版からの保証の変化 | implementation / policy と実装 |
| 外部とのやりとりが失敗したとき | 操作 × 失敗の種類 の扱い | effects / operations |
| 意図的に決めていないこと | unspecified と書かれた箇所 | tables |

画面には AI の要約を入れません。すべて正本と検査器から機械的に導いたものです。

## 検査の内容

| 検査 | 見つけるもの | 重さ |
| --- | --- | --- |
| 決定表の網羅 | どの行にも当たらない入力（境界値の穴、列挙値の組み合わせの抜け） | 拒否 |
| 決定表の排他 | 2つの行に同時に当たる入力（結果が同じかどうかも示す） | 拒否 |
| 到達不能な行 | どんな入力も当たらない行 | 確認 |
| 出力の割り当て | 出力を決めていない行、どの表も決めない出力、複数の表が決める出力 | 拒否 |
| 性質の矛盾 | 同時に満たせない性質（ensures） | 拒否 |
| 性質の自明さ | 入出力の範囲だけで常に成り立ち、何も縛らない性質 | 確認 |
| 表と性質の整合 | 表の結果が性質に違反する行、未規定なのに性質を満たす値が無い入力 | 拒否 |
| 状態と出来事の網羅 | 状態 × 出来事 の組で、遷移も拒否も書かれていない組、扱いが重複した組 | 拒否 |
| 状態の到達性 | 初期状態から到達できない状態、終了状態でないのに抜け出せない状態 | 確認 |
| 失敗の網羅 | 外部作用の失敗の種類のうち、扱いが書かれていないもの | 拒否 |
| 入力の使用 | どの表にも性質にも使われていない入力 | 確認 |
| ユースケース | 未定義のアクター・参照先、何もしないアクター、誰も行わない操作 | 拒否・確認 |
| 画面 | 同じ操作で行き先が複数ある画面、たどり着けない画面、行き止まりの画面、画面から始められないユースケース | 拒否・確認 |
| 連携のデータ | 区分の決まっていないデータ項目、相手に渡してよい区分を超えるデータ | 拒否 |
| 取り消し | 取り消せるかが未定の作用、取り消せない作用の二重実行を防ぐキーの欠落、埋め合わせの手段の欠落 | 拒否 |
| 連携の手順 | 結果を待たずに状態を進める手順、取り消せない作用の後で止まったときの扱いの欠落、確認なしの取り消せない作用、待ち方と呼び方の食い違い | 拒否・確認 |

判定は、SMT ソルバ Z3 で入力空間全体を調べて出します。テストのような抜き取りではないので、
書かれた語彙の範囲内では見落としがありません。具体例は、なるべく 0 に近い値（境界値になりやすい）を選んで示します。

## 実装が仕様どおりか（試作3）

正本に `implementation`（項目と関数の対応）と `policy`（項目ごとに必要な保証）を書くと、`check` と `view` が実装も確かめます。
保証は「事前（なし / テスト済み / 証明済み）× 実行時（監視なし / あり）」で、単位は「実装の関数 × 仕様の項目」です。

| 確かめ方 | 対象 | 結果 |
| --- | --- | --- |
| 証明 | 決定表の関数のうち、if / elif / else・代入・return・比較・四則演算・文字列（列挙値）だけで書かれたもの | 関数を記号実行して Z3 の式にし、「行の条件のもとで実装の値 ≠ 仕様の値」が起こりえないことを示せたら **証明済み** |
| 全件確認 | 状態機械（状態 × 出来事 のすべて）、入力が列挙型・真偽値・狭い整数だけの表 | すべて動かして一致したら **証明済み** |
| テスト | 上のどちらでもないもの（辞書の参照やループなど） | 各入力の端・代表値・仕様と実装に出てくる整数の ±1 の組み合わせと、乱数 300 件（seed 固定）で動かして一致したら **テスト済み** |
| 性質 | ensures のうち出力を含むもの | 出力を決める表の実装を組み合わせて、証明かテストで確かめる |
| 監視 | `@monitor.watch("項目の id")` を付けた関数 | 本番で呼ばれるたびに仕様と比べ、違えば `SpecViolation` で止める。比べる仕様が決まっていなければ動かさない |

所見は次のとおりです。

- 仕様と違う実装は **拒否**。ソルバの反例はそのまま信じず、実際に関数を動かして確かめた具体例（「経過日数=14、商品状態=未開封、支払額=10000 のとき、仕様は 返金額=10000、実装は 返金額=5000」）を出します。
- 方針に届かない実装も **拒否**。結果が正しくても、証明できない書き方で「証明済み」が必要な項目を実装すると受け入れません。
- 実装が対応づけられていない項目、前の版より保証が下がった項目は **確認**。

```yaml
implementation:
  module: impl/shop_impl.py            # 仕様ファイルからの相対パス
  tables: {返金額の決定: refund_amount, 返金方法の決定: refund_method}
  machines: {注文: next_order_state}
policy:
  default: テスト済み                   # 書いていない項目に必要な保証
  返金額の決定: 証明済み
  返金方法の決定: テスト済み＋監視
```

表の関数は入力名（日本語の引数名）で値を受け、出力が1つなら値そのもの、複数なら `{"出力名": 値}` を返します。
列挙値は文字列です。状態機械の関数は `(状態, 出来事)` を受けて次の状態を返し、`None` か例外は拒否です。

例は `examples/impl/` にあります。

- `shop_impl.py`：正しい実装。表・状態機械・性質はすべて証明済み（返金額は記号実行、返金方法と注文は全件確認）、操作2つはテスト済み（筋書きをすべて確認）。返金方法は監視つき
- `shop_impl_bug.py`：全額返金の境界が「14日未満」、返品待ちに商品が届くと「完了」、集荷依頼の結果を待たずに返品待ちにする、決済代行に氏名を渡す、の4つのバグ入り（拒否 4 件、`reports/shop_v2_impl_bug.md`、`views/shop_v2_impl_bug.html`）
- `shop_impl_loop.py`：返金額をループで求める版。結果は正しいがテスト済みまでしか言えず、方針の証明済みに届かないので拒否（`reports/shop_v2_impl_loop.md`）

## 問いに答えて正本を更新する（試作5）

検査器の問いには、答えの形と、答えると正本のどこが変わるかが付いています。レビュー画面のカードにも「問い N・答え方・答えると」を出します。

| 問い | 答え方 | 正本の変わり方 |
| --- | --- | --- |
| どの行にも当たらない入力 | 出力の値か式（決めないなら unspecified） | 表に行が加わる。行の条件は、例の入力を含み、どの行にも当たらない範囲を機械が広げて作る（「経過日数 >= 31 かつ 商品状態 ＝ 開封済み」など）。ほかの行とは重ならない |
| 2つの行の両方に当たる入力 | 使う行の番号 | 選ばなかった行の条件から、選んだ行の条件を除く |
| 状態 × 出来事 の扱いがない | 次の状態か「拒否：理由」 | 遷移か拒否が加わる |
| 外部作用の失敗の扱いがない | 扱い（文章） | on_failure に加わる |
| データ項目の区分がない | 区分 | data.items に加わる |
| 渡してよい区分を超えるデータ | 「渡さない」か「許可する」 | 渡すデータから除く、または相手に渡してよい区分を加える |
| 二重実行を防ぐ仕組みがない | 見分けるデータ項目 | idempotency に入る |
| 結果を待たずに状態を進める | 「待つ」 | 状態の更新の前に await の手順が入る |
| 取り消せない作用の前に確認がない | 確認の内容（文章） | 作用の前に confirm の手順が入る |
| 途中で止まったときの扱いがない | 扱い（文章） | on_interrupt に入る |

答えは問いの番号ごとに書きます（`examples/answers/shop_v1.yaml`）。会話で人が答えた内容を AI がこの形に書き写す想定です。

```yaml
name: 通販の返品（問いに答えた版）
answers:
  1: {返金額: 支払額 // 2}
  4: 拒否：発送済み
  10: 渡さない
  13: 待つ
```

`answer` は元のファイルの書式とコメントを保ったまま答えを書き込み（ruamel.yaml を使用）、新しい版を検査して残りの問いを出します。
答えが新しい漏れを生むこともあります（たとえば性質「返金は支払額を超えない」に反する金額を答えた場合）。そのときは次の問いとして返り、答え直すまで受け入れ可になりません。
`shop_v1.yaml` に 15 問答えた `shop_v1_answered.yaml` は受け入れ可になり、`views/shop_v1_answered.html` で前の版との差分を確かめられます。

### 会話で1問ずつ聞く

一覧を前にまとめて答えるのは重いので、AI が会話で1問だけ聞き、答えを1つ反映するたびに検査し直して次の1問を出す流れも用意しました（[inloop](https://github.com/tazyamah/inloop) と同じく、必要な情報は機械が決まった形でまとめ、AI は聞き方を整えるだけにします）。

`ask` が出す1問ぶんの包み：

```
[AI への指示] この問いを1つだけ、人に会話で聞いてください。…
問い Q7b046f（残り 16 問）：表「返金額の決定」のどの行にも当たらない入力があります
聞くこと：経過日数=30、商品状態=開封済み のとき、どうしますか
答え方：返金額 の値か式（決めないなら unspecified）
答えると：表「返金額の決定」に、条件「経過日数 == 30 and 商品状態 == 開封済み」の行が加わります

関係する部分：
表「返金額の決定」（今ある行）
  1. 経過日数 < 30 and 商品状態 == 未開封 → 返金額=支払額
  …
```

- 選択肢がある問い（状態・行の番号・データの区分・渡さない／許可する、数の穴ならほかの行で使っている値）には番号つきの選択肢が付きます。番号だけの答えを取り違えないよう、AI は選択肢の文字列に直して渡します
- 問いの識別子（`Q…`）は問いの場所から決まるので、版が変わっても同じ問いなら同じです。もう無い問いへの答えは反映しません
- 元の仕様は書き換えず、作業中の版（`-o`、省略時は `<仕様>.work.yaml`）を更新します。答えは `<作業中の版>.answers.jsonl` に追記だけで残し、人が言った言葉（`--said`）もそのまま入れます
- 読めない答え（式の誤りなど）は反映せず、同じ問いを聞き直すよう返します

#### 穴のある表は、先に根底のルールを聞く

穴を1つずつ聞くと似た条件の問いが続き、答えの奥にある考え方がどこにも残りません。そこで穴のある表では、先にルールを聞き（`specgap/rules.py`）、ルールを合わせた表を見せて確かめます。

1. 傾向：経過日数が増えると返金額は？（減る・増える・関係ない・場合による。今の行に合う向きを機械が示す）
2. 列どうしの関係：開封済みの返金額は、未開封のときと比べて？（同じ・半分・0・決めない、または式）
3. 境界：経過日数が 30 のときは、29 以下と 31 以上のどちらと同じ扱い？（列をまとめて1問）
4. ルールから穴を埋めた表を格子で見せ、「これで正しいですか」と聞く（`正しい` なら行が加わる。`セルごとに答える` なら、その表は穴を1つずつ聞く）

```
| 経過日数 | 未開封   | 開封済み      |
|----------|----------|---------------|
| 0〜29    | 支払額   | 支払額 // 2   |
| 30       | 支払額 * | 支払額 // 2 * |
| 31〜3650 | 0        | 0 *           |
```

答えたルールは正本の `rules` に残ります。機械は表とルールを2つの入力の組で照らし合わせ、反する行があれば、近い2点の具体例を付けて拒否します（「日数=30 のとき 額=100、日数=31 のとき 額=120」）。
今の表と合わないルールを答えたときは反映せず、ルールと表のどちらが正しいか聞き直すよう返します。レビュー画面には、表ごとに根底のルールと格子を出します。

```yaml
rules:
  - {id: 経過日数が増えると返金額は増えない, output: 返金額, by: 経過日数, trend: 減る}
  - {id: 開封済みの返金額は未開封のときの半分, output: 返金額, by: 商品状態, from: 未開封, to: 開封済み, then: 返金額 // 2}
  - {id: 経過日数が30のときは29と同じ扱い, output: 返金額, by: 経過日数, from: 29, to: 30, then: 同じ}
```

格子にできる表（整数の入力が1つまでで、列が多すぎない表）だけが対象です。

AI から使うときは MCP サーバー（`python -m specgap mcp`、設定はリポジトリの `.mcp.json`）の道具 `next_question`・`answer_question`・`change_spec` を使います。
レビュー画面は読む場所と記録のままにし、入力欄は付けません。

## 担当者への通知と、統一ルールで決まる条件つきの手順

お店の例を正本と検査だけで作り切る段取りの1段目です。「担当者に通知する」を、文章ではなく連携と手順で書きました（D41〜D43）。

- 担当者への知らせは、操作「担当者に知らせる」で**必ず通知欄に載せ**ます
- メールで送るかどうかは、決定表「メールで知らせるか」（通知の種類 → メールで送る）の**統一ルール**で決めます
- 指針「顧客に影響があり、早めに伝える必要があるものは必ず送る」は、性質（`ensures`）として表に対して証明します。それ以外の行は、運用の都合で決めてよいものとして残します

これを書くために、手順に**条件**（`when: 表.出力`）を付けられるようにしました。

```yaml
steps:
  - {update: 通知欄に載せる}
  - {send: 担当者へのメール, when: メールで知らせるか.メールで送る}
```

- **検査**：条件が指す表と出力があるか、出力が真偽か、表の入力を操作が手元のデータとして持っているか
- **実装の確かめ**
  - 条件の表の入力（選択肢と真偽）の組み合わせごとに、正常の筋書きを動かします
  - それぞれの組み合わせで、表が決めた手順だけを行うかを見ます
  - 表に従わずに送る実装や、通知欄に載せない実装は拒否します（`tests/test_conditions.py`）
- **データ**：選択肢の項目（`通知の種類` など）は、操作がその場で選んで渡してよいことにしました。選択肢にない値は拒否します

### 返金を実行の失敗の扱いをすべて手順に（D44〜D49）

「返金を実行」の残りの扱いを、文章から手順にしました。

| 失敗 | 扱い |
|---|---|
| 決済API.拒否 | 返金失敗として記録し、担当者に通知する |
| 決済API.タイムアウト | 照会し、未返金なら1回だけ再試行。直らなければ返金を保留にして担当者に通知する |
| 返金状況の照会 の失敗 | 返金を保留にする。あとで操作「保留中の返金を照会し直す」が1回だけ照会し直し、できなければ担当者に通知する |
| 返金完了メール.送信失敗 | 送れなかったことを記録する |

これに合わせて、検査と実装の確かめを広げました。

- 条件に**作用の結果**も書けます（`when: 返金状況の照会=返金済み`）。結果ごとに正常の筋書きを動かします
- 別々の分かれ道にある手順どうしは、「結果を待たずに次へ進む」の検査で比べません
- 二重実行を防ぐ鍵は、渡すデータになければ手元のデータから取ります。途中で止まってやり直しても、メールは二重に送られません

### 返品を受け付けるの扱いと実装（D50〜D53）

- **集荷依頼.受付拒否**：集荷依頼が通らなかったと記録し、担当者に通知します。表「メールで知らせるか」でメールでも送ります（D50）
- **集荷依頼の照会**：照会は途中で止まった返品の再開でだけ使うので、再開を操作「処理中の返品を照会し直す」にしました。照会して、依頼済みなら返品待ちにするだけ、未依頼なら集荷依頼から出し直します。照会できなければ1回だけ照会し直し、だめなら返品を保留にして担当者に通知します（D51・D52）
- 再試行で直った作用の結果で後の手順が分かれるときは、結果ごとに筋書きを分けます（`tests/test_returns.py`）

### 不正な支払・重複した発送の知らせを統一ルールにまとめる（D54〜D57）

- 専用の通知（不正な注文の通知・重複した発送の通知）をやめ、担当者への通知にまとめました。通知欄に必ず載り、メールは表「メールで知らせるか」で決まります（不正な注文は送る、重複した発送は送らない）
- 知らせには「詳細画面のリンク」を付けます。リンクから開く画面は入口（entries）に書きます
- 判断の一部の場所だけを、あとの判断が消した（`（削除）` と記録した）ときは、その判断は残りの場所で生きているとみなし、「効いていた場所がない」とは問いません
- これで例の拒否と確認は 0 件になり、操作はすべてテスト済みです

### ユースケースごとの保証

ユースケースの保証を、使う表・状態機械・操作と、使う表の出力にかかる性質のうち、**最も弱いもの**にしました。レポートと画面の「実装が仕様どおりか」に表で出ます。

| ユースケース | 保証 | 最も弱い項目 |
|---|---|---|
| 注文する | 証明済み | 状態機械「注文」 |
| 返品を申し込む | テスト済み | 操作「返品を受け付ける」 |
| 返金を承認する | テスト済み | 操作「返金を実行」 |
| 不正な注文を確かめる | テスト済み | 操作「不正な支払を記録する」 |
| 重複した発送を確かめる | テスト済み | 操作「重複した発送を記録する」 |
| 通知を確かめる | テスト済み | 操作「担当者に知らせる」 |

- 保証がない（実装がない、または違反がある）項目を使うユースケースは、確認として問います
- 画面だけで、確かめられる項目を使わないユースケースは問いません
- 分からないこと：ある操作が送った通知で別の操作（担当者に知らせる）が動く、というつながりは正本に書いていないので、保証の計算にも入っていません

### 完成の判定

お店の例を「正本と検査だけで作り切った」と言える条件を、検査に入れました（`specgap/completion.py`）。レポートの冒頭と画面の「完成の判定」に出ます。

- 拒否と確認が 0 件
- 表・状態機械・性質・操作がすべてテスト済み以上（実装がないものは足りない扱い）
- どのユースケースもテスト済み以上の保証がある
- 範囲外：画面そのものの実装と、途中で止まったときの担当者の作業手順（文章のまま）

例（shop_v1_interviewed.yaml）は完成です。shop_v2.yaml は、画面だけのユースケース「返金状況を確認する」があるので未完成と出ます。

## 失敗の扱いを手順で書き、実装が従っているかを確かめる（試作9）

失敗の扱いは文章（`決済API.通信エラー: 照会して、返金済みでなければ再試行…`）で書いていたので、機械が確かめられたのは「実装が扱った記録を残したか」までした。
試作9では、扱いを文章のまま残しつつ、手順（`do`）でも書けるようにしました。

```yaml
effects:
  返金状況の照会:
    outcomes: [返金済み, 未返金]      # 結果の種類。実装には「結果」として返る
operations:
  - id: 返金を実行
    on_failure:
      決済API.通信エラー:
        text: 決済代行に返金済みかどうかを照会し、返金済みでなければ再試行…   # 人の言葉
        do:
          - case: 返金状況の照会       # 照会して、結果で分ける
            返金済み:
              - {update: 通信エラーと照会の結果をログに残す}
              - resume                 # 続きの手順へ進む
            未返金:
              - {update: 通信エラーと照会の結果をログに残す}
              - {retry: 決済API, times: 1}
              - {update: 返金失敗として記録し、担当者に通知する}   # 再試行しても直らなければ
```

手順に使えるのは、操作の手順と同じ種類（confirm・call・send・await・update）と、`retry`（失敗した作用をもう一度）・`case`（照会の結果で分ける）・`resume`（続きの手順へ進む）です。`resume` がなければ、扱いの手順を終えたところで止まります。

**検査**
- 再試行の相手は、失敗した作用か
- 照会の結果の種類がすべて手順にあるか、結果の種類が決まっているか
- 再試行が最後の手順なら、「再試行しても直らなければ、どうしますか」と問う

例の仕様では、置き換えたとたんにこの問いが出ました。答えは「3回ではなく1回、直らなければ返金失敗」で、D40 に残っています。

**実装の確かめ**
- 失敗の筋書きを、分かれ道ごとに分けて動かします（照会の結果ごと、再試行で直る・直らない）
- 失敗のあとの動きが手順と1つずつ同じかを見ます
- 扱いの中でだけ使う作用（照会）の失敗は、先に元の失敗を起こして扱いに入ってから起こします
- 照会せずに再試行する実装（二重に返金しうる）、再試行の回数が違う実装、直らないときの記録を忘れた実装は、筋書きと違いの箇所つきで拒否します（`tests/test_handlers.py`）

保証の根拠には、手順で確かめた扱いの数と、文章だけで中身を確かめていない扱いの数が並びます。例の実装 `execute_refund`（`examples/impl/shop_v1_impl.py`）はテスト済みです。

## 画面の入口を複数書く（試作8）

画面の流れの入口は `start` の1つだけでした。試作7の会話で出た「通知メールのリンクから、不正な注文の詳細を直接開く」は、判断の前提として文章で残すしかありませんでした。そこで、流れの外から画面を開く入口を `entries` として書けるようにしました。

```yaml
screens:
  - id: 管理者の画面
    start: 不正な注文一覧
    entries:
      - {via: 不正な注文の通知, to: 不正な注文の詳細, link: 不正な注文の詳細画面のリンク}
```

- `via` はリンクを渡す連携（外部作用）、`to` は開く画面、`link` はリンクにあたるデータ項目です
- 検査すること
  - `via` が定義された連携か
  - `link` をその連携で実際に渡しているか
  - `link` が書かれていなければ確認に回します
  - 連携で「…リンク」を渡しているのに、開く画面がどこにも書かれていなければ、確認の問いにします（試作7の例では、この問いが2つ出ました）
  - 「最初の画面からたどり着けない画面」の判定には、入口から入れる画面も含めます
- レビュー画面の遷移図では、入口を点線の箱（✉）から画面へ入る矢印で描きます。前の版との差分にも出ます
- `change` で入口を足すと、判断は `画面:<流れ>:入口:<連携>` を指します。画面の矢印やユースケースを足したときも、`画面:…`・`ユースケース:…` という意味の参照になります

## 道具で受けられなかった答えを受ける（試作7）

試作6までは、会話で出た次の2種類の答えを道具で受けられず、AI が正本を手で直していました。

**「このままでよい」**：確認（warning）の問いには、選択肢に必ず「このままでよい」が付きます。そう答えると判断（`applies_to: [確認:<項目>]`）が残り、以後その項目は「判断 D… で、このままでよいと確認済み」の記録に回ります。拒否（error）の問いには使えません。
機械的に直せない確認の問い（「誰がどの場面で行いますか」など）も、1問ずつ聞く問いの最後に並ぶようになりました。

**選択肢に収まらない答え**：AI は人と変更の中身を確かめてから、変更案を `change`（MCP では `change_spec`）に渡します。

```yaml
- {op: add, path: machines/注文/transitions, value: {from: 発送済み, on: 支払, to: 発送済み}}
- {op: add, path: operations, value: {id: 不正な支払を記録する, steps: [{update: 不正な注文を作り、届いた支払をその注文に登録する}, {send: 不正な注文の通知}]}}
```

- path は「/」区切りで、id を持つ並びは id で選びます。op は add・replace・remove
- 機械は作業中の版に当て、読めない正本になる変更や当てられない変更は反映しません
- 変わったこと（前の版との差分）、変更で新しく出た拒否、答えている問いがまだ残っているかを返します
- 変更は、決めたこと（`--title`）・人の言葉・前提・効いている場所と一緒に判断として残ります

MCP の道具は `next_question`・`answer_question`・`change_spec` の3つになりました。

## 判断を正本のオブジェクトにし、コードは判断に任せる（試作6）

問いへの答えは、そのまま「判断」として正本の `decisions` に残ります（`ask`・`reply`・`answer` のどれで答えても）。
判断には、問い・決めたこと・人の言葉・前提・正本のどこに効いているか（`applies_to`）・置き換えた判断を持たせます。

```yaml
decisions:
  - id: D8
    at: '2026-10-23'
    title: 経過日数が30のときは29と同じ扱い
    question: 経過日数が 30 のときは、29 以下と 31 以上のどちらと同じ扱いですか
    answer: 29 以下と同じ
    said: '1'
    applies_to:
      - ルール:経過日数が30のときは29と同じ扱い
  - id: D9
    title: 表「返金額の決定」に、ルールから決めた 3 行を追加
    supersedes: [D1, D2, D3]         # 穴に直接答えた3つを、ルールから聞き直して置き換えた
    applies_to:
      - 表:返金額の決定:経過日数 == 30 and 商品状態 == 未開封
      ...
```

- 検査器は、有効な判断が指す場所が正本から消えていれば確認に回します（判断を手で書き換えた、あとの変更で消えた、など）
- `python -m specgap decisions <仕様> -o <フォルダ>` で、判断ごとの ADR 形式の Markdown と一覧を書き出します（例：`decisions/shop_v1_interviewed/`）
- レビュー画面には「判断の記録」の節を出し、表の行とルールから判断へたどれます

実装は、表と状態機械で決まることを書き写さず、判断に任せます（`specgap/decide.py`、例：`examples/impl/shop_v1_impl.py`）。

```python
from specgap import decide

refund_amount = decide.table("返金額の決定")
next_order_state = decide.machine("注文")

decide.use(load("shop_v1_interviewed.yaml"))   # 起動時に一度
refund_amount(経過日数=30, 商品状態="開封済み", 支払額=10000)       # → 5000
refund_amount.why(経過日数=30, 商品状態="開封済み", 支払額=10000).reason()
# → D9「表「返金額の決定」に、ルールから決めた 3 行を追加」、…、D8「経過日数が30のときは29と同じ扱い」
```

判断に任せた関数は、表をそのまま実行するので構造上仕様と一致し、保証は「証明済み」になります。その表が性質（ensures）を満たすことは表の検査で証明済みなので、性質も「証明済み」です。
表が値を実装に任せている行は、`decide.table(..., otherwise=関数)` の関数が決めます（この場合は、これまでどおりテストで確かめます）。
失敗の扱いのような文章の判断は、まだ実装との対応を確かめていません。

## 外部とのやりとりの実装（試作4）

操作（operations）の実装は `ctx` だけを受け取る関数で、外部作用は `ctx` を通してしか使えません。
`ctx` は仕様の `uses` にない外部作用を呼ばせず、`sends` と違うデータ（足りない・余計・手元の値と違う）を渡させません。
権限を関数の引数の形で渡す（ケイパビリティ）ので、実装を動かして集めた「使った外部作用と渡したデータ」がそのまま権限の一覧になります。

```python
from specgap.operations import EffectFailure

def execute_refund(ctx):
    if not ctx.confirm("サポート担当が返金額を確認して承認する"):   # steps の confirm と同じ文言
        return
    d = ctx.data                                                    # 手元のデータ
    try:
        ctx.call("決済API", 注文番号=d["注文番号"], 返金額=d["返金額"], 決済ID=d["決済ID"])
    except EffectFailure as f:
        ctx.handled(f.key)                                          # "決済API.タイムアウト" など
        return
    ctx.update("注文を返金済みにする")
    ...
```

`ctx.call`（応答を待つ）・`ctx.send`（送るだけ）・`ctx.await_result`（結果を待つ）・`ctx.update`（状態の更新）が steps の各種類に対応します。
本番では `Context` に本物の外部を呼ぶ `Adapter` を渡せば、同じ権限とデータの確認が呼び出しのたびに行われます。

確かめる筋書きは次のとおりで、すべて動かします（返金を実行なら 9 通り）。

| 筋書き | 確かめること |
| --- | --- |
| 正常 | 手順が steps と同じ順か（違えば「3番目に待つ「集荷依頼」のはずが、更新「注文を返品待ちにする」」のように最初に違う手順を示す） |
| 確認を断る | 断られたあと、外部作用も状態の更新もしないか |
| 失敗（作用 × 失敗の種類） | `ctx.handled` で扱ったか。失敗した作用が成功しないまま後の手順に進んでいないか（同じ作用の再試行は認める） |
| 各手順の直後で止まる | もう一度動かすと残りの手順をやり終えるか。取り消せない作用を二重に実行していないか（同じキーの依頼は外部が1回分として扱う） |

データの値や「2回続けて失敗する」までは尽くしていないので、保証は証明済みではなく **テスト済み** としています。
前の版より実装が使う外部作用やデータが増えたら **確認** に回します（権限の差分）。

例の `shop_impl_bug.py` では、集荷依頼の結果を待たずに注文を返品待ちにする誤りと、決済代行に氏名を渡す誤りが拒否されます。

## 仕様の書き方

```yaml
spec: 返金

enums:
  商品状態: [未開封, 開封済み]

inputs:
  経過日数: {type: int, min: 0, max: 3650}
  商品状態: {type: 商品状態}
  支払額: {type: int, min: 1, max: 1000000, example: 10000}   # example は具体例を作るときの代表値

outputs:
  返金額: {type: int, min: 0}

tables:                      # 決定表：条件ごとに出力を決める
  - id: 返金額の決定
    rows:
      - when: 経過日数 <= 30 and 商品状態 == 未開封
        then: {返金額: 支払額}
      - when: 経過日数 > 30
        then: {返金額: unspecified}   # 意図的に決めない（書き忘れとは区別される）

ensures:                     # 性質：常に成り立つべき条件
  - id: 返金は支払額を超えない
    expr: 0 <= 返金額 <= 支払額

machines:                    # 状態機械：状態 × 出来事 のすべてに遷移か拒否を書く
  - id: 注文
    states: [受付, 完了]
    events: [支払]
    initial: 受付
    final: [完了]
    transitions: [{from: 受付, on: 支払, to: 完了}]
    rejects: [{from: 完了, on: 支払, reason: 終了済み}]

effects:                     # 外部作用：相手、待ち方、やりとりするデータ、取り消せるか、失敗の種類
  決済API:
    system: 決済代行
    mode: sync               # sync（応答を待つ）/ async（送るだけ）
    sends: [注文番号, 返金額, 決済ID]
    reversible: no           # yes / no / compensate（compensate: で埋め合わせる作用を書く）
    idempotency: 注文番号     # 二重実行を防ぐキー
    failures: [タイムアウト, 拒否]

actors:                      # アクター（人）と説明
  購入者: 商品を買った人

usecases:                    # ユースケース：誰が何をするか。関係する表・状態機械・操作を uses で結ぶ
  - id: 返品を申し込む
    actor: 購入者
    uses: [返金額の決定, 返金を実行]

screens:                     # 画面の流れ：操作で画面を移る。usecase を書くとその操作でユースケースが始まる
  - id: 購入者の画面
    start: 注文詳細
    final: [申込完了]
    transitions:
      - {from: 注文詳細, action: 返品を申し込む, to: 申込完了, usecase: 返品を申し込む}

systems:                     # やりとりする外部のシステム
  決済代行: {description: カード決済と返金を行う外部サービス}

data:                        # データの区分と、相手ごとに渡してよい区分
  classes: [一般, 個人情報, 決済情報]
  items: {注文番号: 一般, 返金額: 一般, 決済ID: 決済情報}
  allow: {決済代行: [一般, 決済情報]}

operations:                  # 操作の手順と、使う外部作用の失敗すべてへの扱い
  - id: 返金を実行
    steps:                   # confirm（確認）/ call（応答を待つ）/ send（送るだけ）/ await（結果を待つ）/ update（状態を更新）
      - confirm: サポート担当が返金額を確認する
      - call: 決済API
      - update: 注文を返金済みにする
    on_interrupt: 決済代行に返金状況を照会して再開する   # 途中で止まったときの扱い
    on_failure:
      決済API.タイムアウト: 照会してから再試行する
      決済API.拒否: 失敗として記録する
```

式には `and` / `or` / `not`、比較（`<` `<=` `==` `!=` など、`0 <= x < 30` のような連鎖も可）、
`x in [a, b]`、`+ - * // %`、`a if 条件 else b` が使えます。

## 例

`examples/` に修正前と修正後の仕様が3組あり、`reports/` に検査結果、`views/` に生成したレビュー画面があります。

- `shop_v1.yaml` / `shop_v2.yaml`：通販の返品。ユースケース・画面・決まりごと・状態・システム間連携をひとつにまとめた正本。
  修正前は、決済代行に氏名（個人情報）を渡している、決済APIに二重実行を防ぐキーがない、集荷依頼の結果を待たずに注文を返品待ちにしている、などの漏れがあります。
  修正後は漏れを埋めたうえで、全額返金の期間を30日から14日に短くしているので、差分付きの画面（`views/shop_v2.html`）に「結果が変わる具体例」が出ます

- `refund_v1.yaml`：返金。境界値「ちょうど30日」と「30日より後で開封済み」が抜けている（拒否 3 件）
- `refund_v2.yaml`：問いに答えて埋めた版（受け入れ可、銀行振込の返金方法は意図的に未規定）
- `order_v1.yaml`：注文の状態遷移。「発送済み」での出来事3つと、決済APIの通信エラーの扱いが抜けている（拒否 4 件）
- `order_v2.yaml`：「返品待ち」状態を足して埋めた版（受け入れ可）

## この試作で分からないこと・今後

- 語彙に無い概念（複数通貨、タイムゾーンなど）の考慮漏れは検出できません。AI による候補出しは別途。
- 整数・真偽値・列挙型だけを扱います。文字列、日付、配列、記録型は未対応です。
- 決定表の条件に出力は使えない前提です（入力だけで決まる表）。
- YAML は `on:` や `yes` `no` を真偽値として読むため、`on:` キーと `reversible:` の値は読み込み時に文字列に戻しています。列挙値に `yes` `no` などを使うと同じ問題が起きます。
- 連携の手順は一本道だけで、分岐や並行はまだ書けません。外部からこちらを呼ぶ連携（Webhook など）も未対応です。
- 図の配置は単純な層別レイアウトです。画面や状態が増えると横に長くなり、矢印が箱をかすめることがあります。
- 「結果が変わる具体例」は、両方の版の各行から作った代表的な入力だけで比べています。入力空間全体での差分（ソルバで探す）は未実装です。
- 問いの番号は同じ版の正本に対してだけ意味を持ちます。答えている間に正本が変わったら、問いを出し直す必要があります。
- 「確認」の問い（行き止まりの画面、使われていない入力など）のうち、「このままでよい」という答えを正本に残す書き方はまだありません。
- 答えから新しい状態や新しい外部作用を作ることはできません（既にあるものから選ぶだけ）。仕様の構造を変える答えは、まだ正本を直接直す必要があります。
- 実装の証明は、Python の関数のごく一部の書き方（if・代入・return と式）だけを記号実行します。ループ、関数呼び出し、辞書の参照は証明できずテストに回ります。Python の意味（整数の割り算や比較）と Z3 の意味が食い違う可能性があるため、反例は必ず実行して確かめていますが、「証明済み」の側は変換が正しいことを前提にしています。
- テスト済みの根拠は抜き取りなので、境界値と乱数に当たらない誤りは見逃します（「テスト済み」と「証明済み」を分けているのはそのためです）。
- 操作の実装は、失敗の扱いを記録したか（`ctx.handled`）までしか確かめません。「照会してから再試行する」のような扱いの中身は文章なので、機械では確かめられません。
- 操作の手順は一本道だけです。分岐・並行・複数回の失敗・時間（「1時間後に再送」）は筋書きに入っていません。
- 保証の段階は関数ごとで、関数が別の関数を呼ぶときの伝播（呼んだ先の保証が低いと全体も下がる）はまだありません。
- 次の段階：「このままでよい」という答えの記録、保証の伝播、失敗の扱いを文章でなく手順として書けるようにすること。
