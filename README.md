# specgap：仕様の漏れ検査器とレビュー画面（試作）

人がコードを読まずに仕様だけをレビューする前提で、次のことを行う試作です。

1. **仕様そのものの漏れ**を機械的に見つけ、人がそのまま答えられる問い（「経過日数=30、商品状態=開封済み のとき、どうしますか」）を返す（試作0）
2. 正本（YAML）から**人が判断するためのレビュー画面**を生成する。人は正本を読まず、ユースケース図・画面遷移図・決定表と具体例・状態の表・前の版との差分だけを見る（試作1）
3. **システム間の連携**を正本に書き、検査し、画面に出す。外部への作用は取り消しにくくデータも外に出るので、人の判断が一番集まる場所として扱う（試作2）
4. **実装が仕様に従っていること**を項目ごとに確かめ、保証の段階（証明済み・テスト済み・なし、監視の有無）を出す。正本に書いた方針に届かない実装は受け入れない（試作3）

役割分担は「人の意思を AI が受け取り、会話で仕様が決まり、AI が実装し、抜け漏れは機械が保証する」です。
正本は AI が書き機械が検査するもので、人向けの表示は毎回そこから作り直すので、図と仕様がずれません。

設計の背景は Claude Doc「レビュー面と保証レベル 詳細設計」の「仕様の漏れ検査」節を参照してください。

## 使い方

```
pip install -r requirements.txt
python -m specgap check examples/refund_v1.yaml           # 漏れを検査（Markdown）
python -m specgap check examples/refund_v1.yaml --json    # JSON で出力
python -m specgap view examples/shop_v2.yaml --base examples/shop_v1.yaml -o views/shop_v2.html
                                                          # 前の版との差分付きレビュー画面
python -m specgap check examples/shop_v2.yaml --impl examples/impl/shop_impl_bug.py
                                                          # 実装を差し替えて確かめる（バグ入りの例）
python -m pytest -q                                       # テスト
```

`check` の終了コードは、受け入れ可なら 0、拒否する漏れがあれば 1、仕様ファイルが読めなければ 2 です。
`python -m specgap <仕様>` のようにサブコマンドを省くと `check` になります。

## レビュー画面に出るもの

上から「答えること → 変わったこと → 全体像 → 詳細」の順に並べています。

| 節 | 中身 | 正本のどこから作るか |
| --- | --- | --- |
| 答えてほしいこと | 検査器の問い（拒否・確認）と具体的な入力 | 検査結果 |
| 前の版からの変更 | 結果が変わる具体例（前の版と今の版で同じ入力を計算）、書き換わった箇所 | 2つの版の差分 |
| 誰が何をするか | ユースケース図と一覧 | actors / usecases |
| 画面の流れ | 画面遷移図（追加は緑、削除は赤の破線） | screens |
| 決まりごと | 決定表（穴は「どうしますか」の行として表示）、各行の具体例、いつでも成り立つこと | tables / ensures |
| 状態の移り変わり | 状態遷移図と「状態 × 出来事」の表（空欄が無いことが漏れが無いことを示す） | machines |
| システムのつながり | システム構成図、外に出ていくデータ（区分を超えたものは赤）、取り消せるかと二重実行を防ぐキー | systems / data / effects |
| 処理の流れ | 操作ごとのシーケンス図（問いが出ている手順は赤・黄）と、途中で止まったときの扱い | operations の steps |
| 実装が仕様どおりか | 項目ごとの事前の保証・実行時の監視・根拠（違反は具体例）・方針、前の版からの保証の変化 | implementation / policy と実装 |
| 外部とのやりとりが失敗したとき | 操作 × 失敗の種類 の扱い | effects / operations |
| 意図的に決めていないこと | unspecified と書かれた箇所 | tables |

画面には AI の要約を入れません。すべて正本と検査器から機械的に導いたものです。

## 検査の内容

| 検査 | 見つけるもの | 重さ |
| --- | --- | --- |
| 決定表の網羅 | どの行にも当たらない入力（境界値の穴、列挙値の組み合わせの抜け） | 拒否 |
| 決定表の排他 | 2つの行に同時に当たる入力（結果が同じかどうかも示す） | 拒否 |
| 到達不能な行 | どんな入力も当たらない行 | 確認 |
| 出力の割り当て | 出力を決めていない行、どの表も決めない出力、複数の表が決める出力 | 拒否 |
| 性質の矛盾 | 同時に満たせない性質（ensures） | 拒否 |
| 性質の自明さ | 入出力の範囲だけで常に成り立ち、何も縛らない性質 | 確認 |
| 表と性質の整合 | 表の結果が性質に違反する行、未規定なのに性質を満たす値が無い入力 | 拒否 |
| 状態と出来事の網羅 | 状態 × 出来事 の組で、遷移も拒否も書かれていない組、扱いが重複した組 | 拒否 |
| 状態の到達性 | 初期状態から到達できない状態、終了状態でないのに抜け出せない状態 | 確認 |
| 失敗の網羅 | 外部作用の失敗の種類のうち、扱いが書かれていないもの | 拒否 |
| 入力の使用 | どの表にも性質にも使われていない入力 | 確認 |
| ユースケース | 未定義のアクター・参照先、何もしないアクター、誰も行わない操作 | 拒否・確認 |
| 画面 | 同じ操作で行き先が複数ある画面、たどり着けない画面、行き止まりの画面、画面から始められないユースケース | 拒否・確認 |
| 連携のデータ | 区分の決まっていないデータ項目、相手に渡してよい区分を超えるデータ | 拒否 |
| 取り消し | 取り消せるかが未定の作用、取り消せない作用の二重実行を防ぐキーの欠落、埋め合わせの手段の欠落 | 拒否 |
| 連携の手順 | 結果を待たずに状態を進める手順、取り消せない作用の後で止まったときの扱いの欠落、確認なしの取り消せない作用、待ち方と呼び方の食い違い | 拒否・確認 |

判定は、SMT ソルバ Z3 で入力空間全体を調べて出します。テストのような抜き取りではないので、
書かれた語彙の範囲内では見落としがありません。具体例は、なるべく 0 に近い値（境界値になりやすい）を選んで示します。

## 実装が仕様どおりか（試作3）

正本に `implementation`（項目と関数の対応）と `policy`（項目ごとに必要な保証）を書くと、`check` と `view` が実装も確かめます。
保証は「事前（なし / テスト済み / 証明済み）× 実行時（監視なし / あり）」で、単位は「実装の関数 × 仕様の項目」です。

| 確かめ方 | 対象 | 結果 |
| --- | --- | --- |
| 証明 | 決定表の関数のうち、if / elif / else・代入・return・比較・四則演算・文字列（列挙値）だけで書かれたもの | 関数を記号実行して Z3 の式にし、「行の条件のもとで実装の値 ≠ 仕様の値」が起こりえないことを示せたら **証明済み** |
| 全件確認 | 状態機械（状態 × 出来事 のすべて）、入力が列挙型・真偽値・狭い整数だけの表 | すべて動かして一致したら **証明済み** |
| テスト | 上のどちらでもないもの（辞書の参照やループなど） | 各入力の端・代表値・仕様と実装に出てくる整数の ±1 の組み合わせと、乱数 300 件（seed 固定）で動かして一致したら **テスト済み** |
| 性質 | ensures のうち出力を含むもの | 出力を決める表の実装を組み合わせて、証明かテストで確かめる |
| 監視 | `@monitor.watch("項目の id")` を付けた関数 | 本番で呼ばれるたびに仕様と比べ、違えば `SpecViolation` で止める。比べる仕様が決まっていなければ動かさない |

所見は次のとおりです。

- 仕様と違う実装は **拒否**。ソルバの反例はそのまま信じず、実際に関数を動かして確かめた具体例（「経過日数=14、商品状態=未開封、支払額=10000 のとき、仕様は 返金額=10000、実装は 返金額=5000」）を出します。
- 方針に届かない実装も **拒否**。結果が正しくても、証明できない書き方で「証明済み」が必要な項目を実装すると受け入れません。
- 実装が対応づけられていない項目、前の版より保証が下がった項目は **確認**。

```yaml
implementation:
  module: impl/shop_impl.py            # 仕様ファイルからの相対パス
  tables: {返金額の決定: refund_amount, 返金方法の決定: refund_method}
  machines: {注文: next_order_state}
policy:
  default: テスト済み                   # 書いていない項目に必要な保証
  返金額の決定: 証明済み
  返金方法の決定: テスト済み＋監視
```

表の関数は入力名（日本語の引数名）で値を受け、出力が1つなら値そのもの、複数なら `{"出力名": 値}` を返します。
列挙値は文字列です。状態機械の関数は `(状態, 出来事)` を受けて次の状態を返し、`None` か例外は拒否です。

例は `examples/impl/` にあります。

- `shop_impl.py`：正しい実装。すべて証明済み（返金額は記号実行、返金方法と注文は全件確認）。返金方法は監視つき
- `shop_impl_bug.py`：全額返金の境界が「14日未満」、返品待ちに商品が届くと「完了」になるバグ入り（拒否 2 件、`reports/shop_v2_impl_bug.md`、`views/shop_v2_impl_bug.html`）
- `shop_impl_loop.py`：返金額をループで求める版。結果は正しいがテスト済みまでしか言えず、方針の証明済みに届かないので拒否（`reports/shop_v2_impl_loop.md`）

## 仕様の書き方

```yaml
spec: 返金

enums:
  商品状態: [未開封, 開封済み]

inputs:
  経過日数: {type: int, min: 0, max: 3650}
  商品状態: {type: 商品状態}
  支払額: {type: int, min: 1, max: 1000000, example: 10000}   # example は具体例を作るときの代表値

outputs:
  返金額: {type: int, min: 0}

tables:                      # 決定表：条件ごとに出力を決める
  - id: 返金額の決定
    rows:
      - when: 経過日数 <= 30 and 商品状態 == 未開封
        then: {返金額: 支払額}
      - when: 経過日数 > 30
        then: {返金額: unspecified}   # 意図的に決めない（書き忘れとは区別される）

ensures:                     # 性質：常に成り立つべき条件
  - id: 返金は支払額を超えない
    expr: 0 <= 返金額 <= 支払額

machines:                    # 状態機械：状態 × 出来事 のすべてに遷移か拒否を書く
  - id: 注文
    states: [受付, 完了]
    events: [支払]
    initial: 受付
    final: [完了]
    transitions: [{from: 受付, on: 支払, to: 完了}]
    rejects: [{from: 完了, on: 支払, reason: 終了済み}]

effects:                     # 外部作用：相手、待ち方、やりとりするデータ、取り消せるか、失敗の種類
  決済API:
    system: 決済代行
    mode: sync               # sync（応答を待つ）/ async（送るだけ）
    sends: [注文番号, 返金額, 決済ID]
    reversible: no           # yes / no / compensate（compensate: で埋め合わせる作用を書く）
    idempotency: 注文番号     # 二重実行を防ぐキー
    failures: [タイムアウト, 拒否]

actors:                      # アクター（人）と説明
  購入者: 商品を買った人

usecases:                    # ユースケース：誰が何をするか。関係する表・状態機械・操作を uses で結ぶ
  - id: 返品を申し込む
    actor: 購入者
    uses: [返金額の決定, 返金を実行]

screens:                     # 画面の流れ：操作で画面を移る。usecase を書くとその操作でユースケースが始まる
  - id: 購入者の画面
    start: 注文詳細
    final: [申込完了]
    transitions:
      - {from: 注文詳細, action: 返品を申し込む, to: 申込完了, usecase: 返品を申し込む}

systems:                     # やりとりする外部のシステム
  決済代行: {description: カード決済と返金を行う外部サービス}

data:                        # データの区分と、相手ごとに渡してよい区分
  classes: [一般, 個人情報, 決済情報]
  items: {注文番号: 一般, 返金額: 一般, 決済ID: 決済情報}
  allow: {決済代行: [一般, 決済情報]}

operations:                  # 操作の手順と、使う外部作用の失敗すべてへの扱い
  - id: 返金を実行
    steps:                   # confirm（確認）/ call（応答を待つ）/ send（送るだけ）/ await（結果を待つ）/ update（状態を更新）
      - confirm: サポート担当が返金額を確認する
      - call: 決済API
      - update: 注文を返金済みにする
    on_interrupt: 決済代行に返金状況を照会して再開する   # 途中で止まったときの扱い
    on_failure:
      決済API.タイムアウト: 照会してから再試行する
      決済API.拒否: 失敗として記録する
```

式には `and` / `or` / `not`、比較（`<` `<=` `==` `!=` など、`0 <= x < 30` のような連鎖も可）、
`x in [a, b]`、`+ - * // %`、`a if 条件 else b` が使えます。

## 例

`examples/` に修正前と修正後の仕様が3組あり、`reports/` に検査結果、`views/` に生成したレビュー画面があります。

- `shop_v1.yaml` / `shop_v2.yaml`：通販の返品。ユースケース・画面・決まりごと・状態・システム間連携をひとつにまとめた正本。
  修正前は、決済代行に氏名（個人情報）を渡している、決済APIに二重実行を防ぐキーがない、集荷依頼の結果を待たずに注文を返品待ちにしている、などの漏れがあります。
  修正後は漏れを埋めたうえで、全額返金の期間を30日から14日に短くしているので、差分付きの画面（`views/shop_v2.html`）に「結果が変わる具体例」が出ます

- `refund_v1.yaml`：返金。境界値「ちょうど30日」と「30日より後で開封済み」が抜けている（拒否 3 件）
- `refund_v2.yaml`：問いに答えて埋めた版（受け入れ可、銀行振込の返金方法は意図的に未規定）
- `order_v1.yaml`：注文の状態遷移。「発送済み」での出来事3つと、決済APIの通信エラーの扱いが抜けている（拒否 4 件）
- `order_v2.yaml`：「返品待ち」状態を足して埋めた版（受け入れ可）

## この試作で分からないこと・今後

- 語彙に無い概念（複数通貨、タイムゾーンなど）の考慮漏れは検出できません。AI による候補出しは別途。
- 整数・真偽値・列挙型だけを扱います。文字列、日付、配列、記録型は未対応です。
- 決定表の条件に出力は使えない前提です（入力だけで決まる表）。
- YAML は `on:` や `yes` `no` を真偽値として読むため、`on:` キーと `reversible:` の値は読み込み時に文字列に戻しています。列挙値に `yes` `no` などを使うと同じ問題が起きます。
- 連携の手順は一本道だけで、分岐や並行はまだ書けません。外部からこちらを呼ぶ連携（Webhook など）も未対応です。
- 図の配置は単純な層別レイアウトです。画面や状態が増えると横に長くなり、矢印が箱をかすめることがあります。
- 「結果が変わる具体例」は、両方の版の各行から作った代表的な入力だけで比べています。入力空間全体での差分（ソルバで探す）は未実装です。
- 人の答えを正本に書き戻す会話の部分（問いに答える → AI が正本を直す → 再検査）はまだありません。
- 実装の証明は、Python の関数のごく一部の書き方（if・代入・return と式）だけを記号実行します。ループ、関数呼び出し、辞書の参照は証明できずテストに回ります。Python の意味（整数の割り算や比較）と Z3 の意味が食い違う可能性があるため、反例は必ず実行して確かめていますが、「証明済み」の側は変換が正しいことを前提にしています。
- テスト済みの根拠は抜き取りなので、境界値と乱数に当たらない誤りは見逃します（「テスト済み」と「証明済み」を分けているのはそのためです）。
- 外部作用（operations）の実装はまだ確かめません。副作用の順序や失敗時の扱いを実装と突き合わせるのは今後です。
- 保証の段階は関数ごとで、関数が別の関数を呼ぶときの伝播（呼んだ先の保証が低いと全体も下がる）はまだありません。
- 次の段階：問いへの回答から正本を更新する流れ、外部作用の実装の確認、保証の伝播。
