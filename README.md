# specgap：仕様の漏れ検査器（試作0）

人がコードを読まずに仕様だけをレビューする前提で、**仕様そのものの漏れ**を機械的に見つける試作です。
漏れが見つかると、人がそのまま答えられる問い（「経過日数=30、商品状態=開封済み のとき、どうしますか」）を返します。

設計の背景は Claude Doc「レビュー面と保証レベル 詳細設計」の「仕様の漏れ検査」節を参照してください。

## 使い方

```
pip install -r requirements.txt
python -m specgap examples/refund_v1.yaml          # Markdown で結果を表示
python -m specgap examples/refund_v1.yaml --json   # JSON で出力
python -m pytest -q                                # テスト
```

終了コードは、受け入れ可なら 0、拒否する漏れがあれば 1、仕様ファイルが読めなければ 2 です。

## 検査の内容

| 検査 | 見つけるもの | 重さ |
| --- | --- | --- |
| 決定表の網羅 | どの行にも当たらない入力（境界値の穴、列挙値の組み合わせの抜け） | 拒否 |
| 決定表の排他 | 2つの行に同時に当たる入力（結果が同じかどうかも示す） | 拒否 |
| 到達不能な行 | どんな入力も当たらない行 | 確認 |
| 出力の割り当て | 出力を決めていない行、どの表も決めない出力、複数の表が決める出力 | 拒否 |
| 性質の矛盾 | 同時に満たせない性質（ensures） | 拒否 |
| 性質の自明さ | 入出力の範囲だけで常に成り立ち、何も縛らない性質 | 確認 |
| 表と性質の整合 | 表の結果が性質に違反する行、未規定なのに性質を満たす値が無い入力 | 拒否 |
| 状態と出来事の網羅 | 状態 × 出来事 の組で、遷移も拒否も書かれていない組、扱いが重複した組 | 拒否 |
| 状態の到達性 | 初期状態から到達できない状態、終了状態でないのに抜け出せない状態 | 確認 |
| 失敗の網羅 | 外部作用の失敗の種類のうち、扱いが書かれていないもの | 拒否 |
| 入力の使用 | どの表にも性質にも使われていない入力 | 確認 |

判定は、SMT ソルバ Z3 で入力空間全体を調べて出します。テストのような抜き取りではないので、
書かれた語彙の範囲内では見落としがありません。具体例は、なるべく 0 に近い値（境界値になりやすい）を選んで示します。

## 仕様の書き方

```yaml
spec: 返金

enums:
  商品状態: [未開封, 開封済み]

inputs:
  経過日数: {type: int, min: 0, max: 3650}
  商品状態: {type: 商品状態}
  支払額: {type: int, min: 1, max: 1000000}

outputs:
  返金額: {type: int, min: 0}

tables:                      # 決定表：条件ごとに出力を決める
  - id: 返金額の決定
    rows:
      - when: 経過日数 <= 30 and 商品状態 == 未開封
        then: {返金額: 支払額}
      - when: 経過日数 > 30
        then: {返金額: unspecified}   # 意図的に決めない（書き忘れとは区別される）

ensures:                     # 性質：常に成り立つべき条件
  - id: 返金は支払額を超えない
    expr: 0 <= 返金額 <= 支払額

machines:                    # 状態機械：状態 × 出来事 のすべてに遷移か拒否を書く
  - id: 注文
    states: [受付, 完了]
    events: [支払]
    initial: 受付
    final: [完了]
    transitions: [{from: 受付, on: 支払, to: 完了}]
    rejects: [{from: 完了, on: 支払, reason: 終了済み}]

effects:                     # 外部作用と、その失敗の種類
  決済API: {failures: [タイムアウト, 拒否]}

operations:                  # 操作ごとに、使う外部作用の失敗すべてに扱いを書く
  - id: 返金を実行
    uses: [決済API]
    on_failure:
      決済API.タイムアウト: 照会してから再試行する
      決済API.拒否: 失敗として記録する
```

式には `and` / `or` / `not`、比較（`<` `<=` `==` `!=` など、`0 <= x < 30` のような連鎖も可）、
`x in [a, b]`、`+ - * // %`、`a if 条件 else b` が使えます。

## 例

`examples/` に修正前と修正後の仕様が2組あり、`reports/` に検査結果があります。

- `refund_v1.yaml`：返金。境界値「ちょうど30日」と「30日より後で開封済み」が抜けている（拒否 3 件）
- `refund_v2.yaml`：問いに答えて埋めた版（受け入れ可、銀行振込の返金方法は意図的に未規定）
- `order_v1.yaml`：注文の状態遷移。「発送済み」での出来事3つと、決済APIの通信エラーの扱いが抜けている（拒否 4 件）
- `order_v2.yaml`：「返品待ち」状態を足して埋めた版（受け入れ可）

## この試作で分からないこと・今後

- 語彙に無い概念（複数通貨、タイムゾーンなど）の考慮漏れは検出できません。AI による候補出しは別途。
- 整数・真偽値・列挙型だけを扱います。文字列、日付、配列、記録型は未対応です。
- 決定表の条件に出力は使えない前提です（入力だけで決まる表）。
- YAML は `on:` を真偽値として読むため、読み込み時に文字列に戻しています。列挙値に `yes` `no` などを使うと同じ問題が起きます。
- 次の段階：仕様の差分（変更前後の比較）をレビュー面の形で出す、実装言語のコアと保証レベルの試作へ進む。
